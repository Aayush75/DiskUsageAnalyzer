# Release procedure

1. Review `docs/SAFETY.md`, current validation evidence, known limitations and the dependency audit. Run `eng/Build.ps1 -UiTests -Coverage`; no failed/skipped safety check is acceptable.
2. Review the SDK/runtime patch and all lockfiles. `dotnet restore --locked-mode` must succeed. Inspect source and staged diff for credentials, private reports and unintended mutation code.
3. Install the trusted Inno Setup 6.7.3 compiler, or supply `-Compiler` to `eng/Package.ps1`. Run `eng/Package.ps1 -Version <version> -Installer`. The script produces a self-contained ZIP, per-user installer, dependency inventory/upstream notices, and SHA-256 checksums. Existing release ZIPs are not silently overwritten.
4. Test the exact packaged executable via the UI harness's packaged smoke mode and on a clean supported Windows 11 x64 VM without a SDK, offline, as a standard user. Test install, upgrade, uninstall confirmation, retained history/recovery, unusual install paths, high DPI, Narrator and high contrast. Record checksums and results. Do not replace unavailable environments with a claim of success. The optional `dotnet run --project tests/DiskUsageAnalyzer.UITests -c Release -- --installer artifacts/releases/DiskUsageAnalyzer-0.1.0-win-x64-setup.exe artifacts/installer-tests` checks an owned installation/reinstall/uninstall journey and refuses to replace an existing registered installation.
5. Sign artifacts only with an available verified publisher certificate in a trusted release environment; otherwise label them unsigned. Never expose secrets to fork pull requests. An unsigned checksum does not authenticate a publisher.
6. Create a reviewed source commit/tag and keep it immutable. A rollback uses `git revert` or an earlier artifact; it does not restore user deletion. Preserve app data/schema compatibility.
7. Identify the intended GitHub repository/account and visibility. No remote currently exists. Before publication, enable private vulnerability reporting, update `SECURITY.md` with its verified link, configure branch protection/required CI, and publish synthetic screenshots plus a readable changelog/known limits. Never invent a remote or claim publication without checking it.
8. Publish a GitHub prerelease for initial field validation. A stable v1 release additionally needs clean-machine/upgrade/accessibility evidence and independent user feedback. Do not claim all gates in the original plan have been met merely because a local build works.

CI prepares unsigned portable artifacts but deliberately does not automatically publish or silently install them. A signing identity, external clean VM, Narrator review, and public repository configuration remain operator-controlled release prerequisites.
